# Kerberos defaults: configuration is not a login

Kerberos is how applications authenticate to the accelerator control system; no other authentication method is supported there. Some read-only operations currently work without authentication, but **modifications require a Kerberos ticket**. A configuration file tells Kerberos tools which realm (identity domain) and servers to use; a ticket is a time-limited credential obtained separately at runtime. This template supplies defaults, not a ticket-acquisition workflow. If your app calls ACSys, its authentication needs depend on the operations it performs, not on whether you keep the sample CLI/PyQt code. See [Quickstart](quickstart.md) and [customizing the example](application.md#replace-the-example-step-by-step) for your app, and [CI and deployment](deployment.md) for normal releases and admin-managed Harbor access. You do not need to operate the shared environment yourself.

## What is already configured

The checked-in [Fermilab configuration](../.kerberos/krb5.conf) sets `FNAL.GOV` as the default realm and lists Fermilab domain mappings and KDCs (servers that issue tickets). These are connection settings, **not** credentials or permission to use a service. The [CLI image's base stage](../Dockerfile) installs `krb5-libs` and `krb5-workstation` and copies that file to `/etc/krb5.conf`. Both CLI builder and runtime inherit it; the builder also installs `krb5-devel` for compiling dependencies, but the CLI runtime does not install that development package separately.

The [Xpra GUI builder and runtime](../Dockerfile) use the externally maintained `ap-python-xpra-base` image, not the CLI base. This repository's Dockerfile does **not** copy its checked-in [config file](../.kerberos/krb5.conf) to the GUI image; any GUI Kerberos libraries and configuration depend on that external base and cannot be verified from this repository. Check the base's configuration with its maintainers if your GUI app needs Kerberos. The Xpra builder installs `krb5-devel`. The [CI workflow](../.github/workflows/ci-cd.yaml) requests `libkrb5-dev` on the integration host; this does not obtain runtime tickets.

## If your app needs different settings

Only change Kerberos configuration if your own service needs it. For the CLI image, edit [`.kerberos/krb5.conf`](../.kerberos/krb5.conf) and rebuild; an already-built image will not change. For the GUI image, editing this checked-in file alone has no effect because the GUI stages use the maintained base instead of copying it. Coordinate any app-specific GUI settings or runtime ticket workflow with the maintainers of the base or deployment environment, rather than provisioning shared infrastructure yourself.

## Runtime tickets and control-system access

Libraries and configuration do **not** acquire a ticket or create a credential cache. The [sample ACSys client](../src/ap_python_starter_kit/acsys_client.py) opens a DPM connection but has no ticket-acquisition logic. Neither the [startup script](../docker/start.sh) nor the [local run commands](../Makefile) provisions or forwards credentials. The demo's read request may work without authentication where read-only access is allowed; that does not mean your app can modify controls. Any operation that changes the accelerator control system requires a Kerberos ticket, and Kerberos is its only supported authentication method. Network access and service permissions still matter. Arrange the approved runtime Kerberos workflow for **your app** with the environment maintainers; it is not provided here. Do not commit credentials or bake them into an image. Xpra's [unauthenticated default browser endpoint](container.md#xpra-lifecycle-and-security) is a separate access-control concern, not Kerberos authentication.
