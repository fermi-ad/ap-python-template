# Kerberos configuration and runtime tickets

Kerberos is the only supported authentication method for the accelerator control system. Some read-only operations currently work without authentication; **modifications require a Kerberos ticket**. A configuration file tells Kerberos tools which realm (identity domain) and servers to use; a ticket is a time-limited credential obtained separately at runtime. This template supplies configuration defaults. Arrange ticket acquisition separately if your app needs it. If your app calls ACSys, its authentication needs depend on the operations it performs, whether you keep the sample CLI/PyQt code or replace it. See [Quickstart](quickstart.md) and [customizing the example](application.md#replace-the-example-step-by-step) for your app, and [CI and deployment](deployment.md) for normal releases and admin-managed Harbor access.

## What is already configured

The checked-in [Fermilab configuration](../.kerberos/krb5.conf) sets `FNAL.GOV` as the default realm and lists Fermilab domain mappings and KDCs (servers that issue tickets). These connection settings supply neither credentials nor permission to use a service. The [CLI image's base stage](../Dockerfile) installs `krb5-libs` and `krb5-workstation` and copies that file to `/etc/krb5.conf`. Both CLI builder and runtime inherit it; the builder also installs `krb5-devel` for compiling dependencies, while the CLI runtime does not install that development package separately.

The [Xpra GUI builder and runtime](../Dockerfile) use the externally maintained `ap-python-xpra-base` image. This repository's Dockerfile copies the checked-in [config file](../.kerberos/krb5.conf) only to the CLI image; any GUI Kerberos libraries and configuration depend on the external base and cannot be verified from this repository. Check the base's configuration with its maintainers if your GUI app needs Kerberos. The Xpra builder installs `krb5-devel`. The [CI workflow](../.github/workflows/ci-cd.yaml) requests `libkrb5-dev` on the integration host; runtime tickets must be obtained separately.

## If your app needs different settings

Only change Kerberos configuration if your own service needs it. For the CLI image, edit [`.kerberos/krb5.conf`](../.kerberos/krb5.conf) and rebuild; an already-built image will not change. For the GUI image, editing this checked-in file alone has no effect because the GUI stages use the maintained base instead of copying it. Coordinate any app-specific GUI settings or runtime ticket workflow with the maintainers of the base or deployment environment, rather than provisioning shared infrastructure yourself.

## Runtime tickets and control-system access

Libraries and configuration alone cannot acquire a ticket or create a credential cache. The [sample ACSys client](../src/ap_python_starter_kit/acsys_client.py) opens a DPM connection without ticket-acquisition logic. The [CLI startup script](../docker/start-cli.sh), [GUI startup script](../docker/start-gui.sh), and [local run commands](../Makefile) do not provision or forward credentials. The demo's read request may work where unauthenticated read-only access is allowed. To modify controls, your app needs a Kerberos ticket; network access and service permissions still matter. Arrange the approved runtime Kerberos workflow for **your app** with the environment maintainers; it is not provided here. Do not commit credentials or bake them into an image. Xpra's [unauthenticated default browser endpoint](container.md#xpra-lifecycle-and-security) controls access to the browser-served window separately from Kerberos authentication to ACSys.
